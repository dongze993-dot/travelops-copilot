# v2 模型评测与证据规范

## 目的

v1 的 42 条 HTTP 用例保护确定性 API 契约；它们不等于大模型质量。v2 单独使用 `evals/v2-llm.jsonl` 和 `scripts/run_model_eval.py` 记录真实模型增强路径的结构、来源和降级行为，避免把“接口能跑”误写成“模型效果好”。

评测输入全部是本仓库作者编写的合成请求，知识数据也全部是合成资料。模型输出只允许解释确定性候选，不可用作真实旅行建议。

## v2 测试集

`v2-llm` 当前有 30 条固定案例：

| 组别 | 数量 | 用途 |
| --- | ---: | --- |
| 可调用模型的正常请求 | 18 | 覆盖 9 个演示城市、多天、多人、兴趣组合和不同预算档位；要求模型返回通过来源白名单校验的 JSON。 |
| 极低预算 | 6 | 验证预算校验失败时不调用模型、保留确定性说明。 |
| 未知城市 | 6 | 验证无同城来源时不调用模型、不伪造来源。 |
| **总计** | **30** | 这是版本化的工程评测集，不是用户样本或现实准确率数据。 |

## 首次真实 API 评测前

1. 在项目根目录复制 `.env.example` 为 `.env`，或使用已创建的本地 `.env`；只在 `DEEPSEEK_API_KEY=` 后粘贴密钥，绝不提交或发到聊天。
2. 在 DeepSeek API 控制台确认账户确实有可用额度，并将控制台显示的模型标识填入 `TRAVELOPS_LLM_MODEL`。
3. 将 `TRAVELOPS_LLM_ENABLED=true`。其他默认值保持不变即可。
4. 启动服务：

   ```bash
   .\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
   ```

5. 在另一个终端运行真实模型评测：

   ```bash
   .\.venv\Scripts\python.exe scripts/run_model_eval.py --base-url http://127.0.0.1:8000 --suite evals/v2-llm.jsonl --require-llm
   ```

`--require-llm` 会确保 18 条可调用模型的案例确实返回 `llm_augmented`，而不是静默降级。报告会写入 `reports/model-eval-<UTC 时间>.json`。不要手工修改报告数字；修复问题后用新提交和新报告重新运行。

## 报告里的指标

| 指标 | 计算方式 | 能说明什么 | 不能说明什么 |
| --- | --- | --- | --- |
| 契约与受控来源通过率 | 通过案例 / 运行案例 | HTTP 行为、来源 ID 和逐日覆盖的可观察约束 | 真实旅游正确率或用户满意度 |
| 模型增强率 | `llm_augmented` 案例 / 18 条可调用模型案例 | 在本次配置下模型路径实际成功比例 | 供应商 SLA 或长期可用性 |
| 来源白名单与逐日覆盖率 | 来源和天数结构均有效的模型输出 / 已增强案例 | 模型输出是否越过受控来源边界 | 文案是否“有创意”或现实事实是否正确 |
| 调用/端到端 P50、P95 | 本次报告中成功请求的分位数 | 该机器、该模型、该网络、该样本上的可复跑基线 | 线上性能承诺 |
| token 记录覆盖/总量 | 供应商返回 usage 的案例及 token 汇总 | 本次运行的可审计用量依据 | 固定成本；价格需另记价目日期和口径 |
| 降级原因分布 | `fallback_code` 的计数 | 常见的配置、限流、网络或输出校验失败类别 | 真实用户错误率 |

## 建议的迭代方式

首次得到真实报告后，不要只看总通过率。优先抽取失败样例，按以下顺序改进：

1. 不合法 JSON 或漏天数：收紧提示词示例、调整 token 上限；
2. 未知 `source_id`：检查允许 ID 是否清晰，并保留白名单回退；
3. 超时/限流：记录发生时间、模型、请求数和重试结果，不盲目增加重试；
4. 文案不清楚但结构正确：从固定集抽 10–20 条，以相关性、可读性、可追溯性、边界诚实四项人工评分 1–5 分，并保存原始评分表；
5. 每项修改对应一个真实 Git 提交，再重新跑完整套件。

不要把单次报告写成“生产准确率”“真实用户满意度”或“节省成本”。只有报告里的具体、可复跑数字才可进入简历。
