# 评测与指标口径

## 原则：先有报告，再写数字

本仓库提供 `evals/v1.jsonl` 和 `scripts/run_eval.py`，用于生成可复跑的本地评测报告。**在 `reports/` 中存在实际运行产物之前，本项目不声称任何通过率、平均耗时、覆盖率、节省成本或用户效果。**

### 当前本地基线（2026-09-20）

原始报告 [`../reports/eval-v0.1-final.json`](../reports/eval-v0.1-final.json) 记录了 Windows 11 / Python 3.12.14 中的一次黑盒运行：`synthetic-v1` 的 12 条合成知识记录、`evals/v1` 的 42 条 HTTP 契约用例，42/42 通过；成功请求延迟 P50 为 5.19 ms、P95 为 16.05 ms。这是单机、单次、合成数据下的回归基线，不能外推为线上性能、真实旅游准确率或业务效果。

如果将数字写进简历、README 或演示材料，至少同时保留：

- Git commit SHA；
- 评测集版本与用例总数；
- 运行日期、Python 版本、操作系统/容器信息；
- 命令行和完整原始 JSON 报告；
- 失败用例及是否经过人工复核。

## 核心指标

| 指标 | 公式 | 用途 | 边界 |
| --- | --- | --- | --- |
| 契约通过率 | `通过自动断言的用例数 / 已执行自动用例数 × 100%` | 检查 HTTP 状态、响应字段和基本约束 | 不代表答案“有用”、也不代表真实业务质量 |
| 来源字段覆盖率 | `含可用来源标识的推荐项数 / 推荐项总数 × 100%` | 检查可追溯性 | 合成 `synthetic://` 只证明演示数据可追溯，不证明现实准确性 |
| 预算校验一致率 | `预算相关断言通过数 / 已执行预算断言数 × 100%` | 检查总额/限制关系 | 不代表真实价格、税费或库存正确 |
| 输入拒绝正确率 | `非法输入得到预期 4xx 的用例数 / 非法输入用例数 × 100%` | 检查边界处理 | 不覆盖安全攻防或所有非法输入 |
| 工单契约通过率 | `工单创建/查询通过断言数 / 已执行工单断言数 × 100%` | 检查模拟接口闭环 | 不代表真实 CRM 集成成功 |
| P50 / P95 延迟 | 对成功请求耗时排序后取相应分位值 | 发现本地回归 | 需注明机器、并发、缓存和网络条件，不能外推生产性能 |

## 报告格式与复跑

```bash
python scripts/run_eval.py --base-url http://127.0.0.1:8000 --suite evals/v1.jsonl
```

脚本以 HTTP 黑盒方式访问服务，默认只运行标为 `automatable: true` 的用例。报告应记录：

- suite 文件内容的 SHA-256；
- 每条用例的请求、HTTP 状态、耗时、通过/失败断言；
- 汇总数（总数、通过、失败、跳过、耗时）；
- 运行入口、Python 版本、时间戳和服务基地址。

评测脚本本身不访问 `app/` 的内部函数或数据结构，因此它也能捕捉到路由、序列化和容器部署层的问题。

## 人工评审维度

自动断言很适合查回归，却不足以判断体验。每次发布前可抽样 10 条规划响应，按以下维度由人打分（0/1 或 1–5），并把表格放在真实报告旁：

| 维度 | 问题 |
| --- | --- |
| 约束尊重 | 天数、人数、预算和兴趣有没有明显被忽略？ |
| 可读性 | 结果是否有按天结构、下一步建议和可理解的失败提示？ |
| 可追溯性 | 推荐项是否可定位到来源 ID？ |
| 边界诚实 | 是否明确这是合成演示数据，避免现实承诺？ |
| 人工交接 | 请求工单时是否清楚说明是模拟状态？ |

人工评审应保留抽样方法、评审人、标准和原始记录；不要把“个人主观觉得不错”换算成虚构的用户满意度。

## 不应计算或宣传的指标

在没有真实授权数据、合规埋点和对照实验前，不要声称：真实用户数、转化率、节约工时、营收提升、真实检索准确率、客户满意度、生产可用性或“上线成功”。这些指标需要明确的数据口径、样本、时间窗和业务授权。

## 建议的简历表述

当且仅当已运行并保存报告后，可使用类似：

> 针对 `evals/v1` 的 42 条可自动执行用例运行本地 HTTP 回归评测，生成 JSON 报告并记录失败分类；指标仅覆盖合成数据和 API 契约，不代表真实旅游业务效果。

这种写法展示了工程证据，同时不会夸大项目。
